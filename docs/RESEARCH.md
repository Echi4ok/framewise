# Исследование модели и проверка визуального grounding

Дата исследования — 5 ноября 2026 года. Приложение получает готовые фотографии, выбирает информативные кадры и связывает видимые детали с рамками. Основной риск — правдоподобное описание, для которого в указанном кадре нет визуального подтверждения.

## Основания для короткого списка

Qwen3-VL обучалась на image captioning, grounding и multi-image задачах. В техническом отчёте координаты нормализованы в диапазон 0–1000. Сравнение небольших Instruct-вариантов в таблице 4 даёт RefCOCO-avg 89,0 для 4B и 89,1 для 8B. Этот близкий результат требует проверки именно фотографий задания, особенно мелких деталей и нескольких ракурсов. Архитектура сочетает vision encoder, merger и языковую модель. [Технический отчёт Qwen3-VL, разделы 2, 3.2.4, 5.5, таблица 4](https://arxiv.org/pdf/2511.21631)

В короткий список вошли Qwen3-VL-4B-Instruct и Qwen3-VL-8B-Instruct в GGUF Q4_K_M. Они доступны локально и могут обслуживать OpenAI-совместимый Chat Completions endpoint. CLIP возвращает представления и оценки сходства изображений с текстом. Для связки «описание детали + рамка» выбран генеративный VLM. [Qwen3-VL](https://github.com/QwenLM/Qwen3-VL), [CLIP API](https://github.com/openai/CLIP#api), [llama.cpp server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)

Облачные Qwen3.7 Flash и Gemini 3.8 Flash рассмотрены по документации как альтернативы. У Qwen есть OpenAI-совместимый API и JSON mode, у Gemini опубликован пример object detection с рамками. Для этой работы облачные ключи не предоставлены, поэтому качество и задержка этих endpoint не измерялись. Визуальный результат JSON mode всё равно проходит серверную проверку структуры, идентификаторов и геометрии. [Qwen vision](https://www.alibabacloud.com/help/en/model-studio/vision), [Qwen structured output](https://www.alibabacloud.com/help/en/model-studio/qwen-structured-output), [Gemini image understanding](https://ai.google.dev/gemini-api/docs/image-understanding)

## Среда испытаний

- Windows, RTX 5070 12 GB, 32 GB RAM.
- Изолированный llama.cpp b12124, официальные Windows CUDA 13.4 binaries и runtime. Драйвер NVIDIA 610.88.
- OpenAI-совместимый endpoint `http://127.0.0.1:11436/v1`, один слот, контекст 12 288 токенов, все доступные слои на GPU, Flash Attention.
- Минимум 1024 и максимум 1536 image tokens на кадр. Низкий минимум был исключён после предупреждения runtime об ухудшении grounding. [Обсуждение llama.cpp](https://github.com/ggml-org/llama.cpp/issues/16842)
- Изображения EXIF-нормализованы, JPEG, длинная сторона не более 1600 px. Для анализа кадры передаются отдельно с точным `image_id`, для выбора используется contact sheet.
- `temperature=0.1`, `seed=42`, `response_format=json_schema`. Проверка схемы не подтверждает истинность описания.

Установленный Ollama 0.30.7 уходил в CPU fallback. В его CUDA-папке оказались незавершённый installer fragment и неполный набор библиотек. Испытания перенесены в отдельную папку runtime. Системная установка и драйвер не менялись. Команда `llama-server --list-devices` обнаружила RTX 5070, фактическая загрузка VRAM была проверена через `nvidia-smi`.

## Протокол

Fixtures в `evaluation/fixtures/cases.json` охватывают кепку с маленьким текстом и нашивкой, чемодан с ручкой/внутренней частью/замком, обувь с противоречащим каталогом и тайтсы с рекламными подписями. Это небольшой выбранный вручную development set. Он использовался при изменении prompt и не является независимым тестовым набором.

Проверки разделены по смыслу.

1. **Контракт** — JSON, положительные рамки, допустимые image IDs, 3–5 признаков при успешном анализе, отсутствие точных повторов описания и региона.
2. **Визуальная опора** — ручная проверка соответствия текста кадру. Материалы, комфорт, скрытая технология и точные названия персонажей учитываются как неподтверждённые, когда их нельзя прочитать или увидеть.
3. **Grounding** — отдельные запросы с девятью заданными деталями. Результат сравнивается с приблизительными ручными рамками через IoU, порог 0,5. Модель не получает эталонные координаты. Разница между цельной деталью и её частью проверяется на overlay.
4. **Выбор фото** — отделение настоящих ракурсов от размерной таблицы и информационных карточек, валидность выбора на contact sheet из 15 и 20 изображений.
5. **Отказ при нехватке данных** — белый кадр и отдельная размерная таблица.

В `evaluation/results/` сохранены raw responses, извлечённый JSON, точный system prompt, image IDs, usage, wall-clock duration и overlays. Запросы отправлялись последовательно. Время включает API-вызов, но зависит от прогрева GPU и кэшей runtime. Его следует воспринимать как наблюдение для этих запусков, а не как гарантированный SLA или изолированный эффект prompt.

## Итерации

Начальный prompt просил найти особенности и передавал каталог вместе с изображениями. Qwen3-VL 4B описала скрытую амортизацию Nike Air и низкий ворот, хотя на фотографиях видна высокая обувь. У тайтсов появились утверждения о комфорте, вентиляции и отведении влаги. Все эти ответы могли быть синтаксически корректными.

Первая строгая версия явно ограничила вывод видимыми деталями. На противоречащей каталогу обуви она стала возвращать `insufficient_evidence`, а при выборе кадров включила размерную таблицу. Это стало основанием изменить передачу данных.

В версии v3 описание каталога исключено из запроса анализа. Название и описание остаются видимыми пользователю в карточке. Модель получает фотографии как единственный источник визуальных признаков. Для выбора фото введены буквенные метки `PHOTO A…T`, которые сервер сопоставляет с image IDs. Это устраняет неоднозначность между номером ячейки и числовым суффиксом ID. Добавлены ограничения на функциональные выводы из рекламных надписей и догадки об именах персонажей.

После одинакового сравнения двух моделей отдельно проверен контекст только с названием товара. Он указывает целевой объект среди одежды на модели, сохраняя фотографии единственным доказательством признаков. Сравнивались два случая — куртка в двух ракурсах и обувь с противоречащим названием/описанием. Обе стратегии описывали куртку, а name-only сохранил видимые признаки обуви без утверждений об Air или коже. Дополнительный контроль с одной размерной таблицей при name-only вернул `insufficient_evidence`. В финальном приложении используется name-only для выбора целевого объекта, полное описание в запрос не передаётся. Имя сериализуется как JSON-строка и обозначено недоверенным контекстом.

## Результаты и границы применимости

Для основного сравнения заморожен один system prompt v3, одинаковые входные фотографии и отсутствие текста каталога. Исторические имена серий `4b-production-final` и `8b-production-final` относятся именно к этому сравнению. Окончательный name-only контекст проверялся затем отдельными exploratory-запросами. Он меняет вход production-приложения, поэтому приведённые ниже числа нельзя выдавать за измерение уже этой финальной конфигурации.

| Проверка development set | Qwen3-VL 4B Instruct | Qwen3-VL 8B Instruct |
| --- | --- | --- |
| Первый ответ проходит контракт, 10 запросов | 8/10 | 9/10 |
| Контракт на 5 запросах с настоящими фото | 3/5 | 4/5 |
| Корректный отказ на белом кадре и таблице | 2/2 | 1/2 |
| Допустимые image IDs при выборе фото | 3/3 | 3/3 |
| Текст полностью подтверждается, ручные метки | 13/17 признаков | 15/17 признаков |
| Рамка достаточно сфокусирована, ручные метки | 12/17 | 11/17 |
| Текст + рамка + физическая деталь товара | 8/17 | 10/17 |
| То же с исключением семантических повторов | 6/17 | 9/17 |
| Отдельный fixed-target grounding, IoU ≥ 0,5 | 7/9 | 7/9 |
| Средний IoU fixed-target grounding | 0,8077 | 0,7813 |
| Медиана 5 запросов анализа в этой серии | 4,547 с | 7,438 с |

Ручные метки относятся к конкретным 17 признакам в каждой серии. Пограничные решения и пояснения каждого признака записаны в `evaluation/manual-review.json`. Измерение первого ответа выполнено до repair-вызова приложения. Поэтому syntactically valid `status=ok` с таблицей считается прошедшим контракт, но провалившим смысловой отрицательный контроль. Выбор из 20 кадров подтвердил работоспособность меток и mapping. 8B выбрала A/C/K/S, 4B A/B/C/F. У 8B набор охватил костюм целиком, детали брюк и манжеты, но также включил кадр с рекламной подписью. Эта проверка не доказывает оптимальный выбор ракурсов на другом каталоге.

Выбран **Qwen3-VL-8B-Instruct Q4_K_M**. На этом небольшом наборе у него меньше структурных отказов первого ответа и больше совместно подтверждённых деталей. 4B быстрее и требует меньше VRAM. У 8B нет преимущества по отдельному fixed-target IoU, и часть рамок остаётся недостаточно точной. Решение основано на ограниченном улучшении целого сценария, а не на обещании универсальной точности. Для 8B измерена загрузка около 10,4 GiB общей занятой VRAM вместе с другими приложениями на этом компьютере.

Проверены две дополнительные идеи.

- **Второй проход верификации и уточнения bbox** на сохранённых признаках кепки и тайтсов добавил 8,703 и 9,641 с. Модель должна была отклонить неподтверждённые описания и повторы, но оставила все 8. Число достаточно сфокусированных рамок осталось 5/8. При этом ложная транскрипция ленты повторилась, а повторяющиеся логотипы не исчезли. Такой проход в production не добавлен.
- **Прямой запрет OCR-транскрипции** проверен одним дополнительным запросом на кепке. Несмотря на инструкцию описывать только расположение, форму и цвет, ответ снова содержал угаданный текст ленты. Улучшение не подтверждено, эта версия не принята.

После основной серии проверены два свежих внешних изображения через настоящий API импорта по URL.

- На сцене с выпечкой название «Выпечка на фотографии» в финальном v3 + name-only дало HTTP 200 за 5,86 с. Среди четырёх признаков модель описала ложку, чашку с ягодами и стаканы на фоне. Это выявило ограничение внимания к целевому объекту при нескольких предметах в кадре. Источник и ответ сохранены в `evaluation/public-product-url-verification.json`. [Исходная сцена](https://storage.googleapis.com/generativeai-downloads/images/scones.jpg)
- Дополнительный target-only guard v4 на той же сцене завершился HTTP 502 `invalid_model_response` за 7,61 с после двух невалидных ответов. Эта попытка сохранена в `evaluation/public-product-url-v4.json`. Запись содержит итоговую ошибку API, поэтому детализация сырых ответов модели для этой пробы ограничена. Guard отклонён, приложение возвращено к неизменённому system prompt v3.
- URL товарного изображения туши успешно импортирован с HTTP 201. Последующий анализ дал HTTP 200 и пять признаков за 6,48 с. Этот внешний сценарий сохранился в `evaluation/public-retail-url-verification.json`. Содержательную точность признаков и рамок следует оценивать отдельно от успешного завершения API-сценария. [Карточка примера](https://dummyjson.com/products/1), [исходное изображение](https://cdn.dummyjson.com/product-images/beauty/essence-mascara-lash-princess/1.webp)

Эти свежие exploratory-пробы расширяют наблюдения за поведением приложения. Они также показывают, что произвольная многопредметная сцена может переключить внимание модели на фон даже при указанном названии товара. Вывод о переносимости качества на любые новые изображения требует более широкой независимой проверки.

В приложении остаётся один анализ выбранных фото, проверка схемы/геометрии/точных повторов и один ограниченный repair-вызов при невалидном ответе. Связанная подсветка позволяет проверить регион. Проверка JSON не делает визуальное утверждение достоверным. В исследовании сохранены неподтверждённый текст внутренней ленты, описание рисованной бороды как «шерсти», повторяющиеся логотипы и рамки, обрезающие знак. Пользователь может изменить набор изображений и повторить анализ.

Основные fixtures из четырёх товаров позволяют обнаружить конкретные дефекты, но не дают основания заявлять точность на произвольном каталоге. В дополнительных запросах использованы куртка и костюм с 20 кадрами. При переносе в production потребуется независимая размеченная выборка с разными категориями, плохим освещением, обрезанными объектами и неоднозначными мелкими деталями. Prompt и способ передачи данных менялись одновременно в exploratory-итерациях, поэтому их отдельные причинные эффекты не изолированы. Для этой реализации человеческое подтверждение набора фото и видимые связанные рамки позволяют пользователю проверить ответ.

SHA256 system prompt и исходных файлов, JPEG recipe и хеши фактически отправленных изображений записаны в результатах. Для ранних серий хеши восстановлены из сохранённых ID и фиксированного recipe, что явно помечено `hashes_reconstructed_from_recorded_recipe`. Проверка `evaluation/check_provenance.py` подтвердила совпадение system prompt, порядка image IDs и JPEG payload во всех 10 парных случаях. Результат сохранён в `evaluation/provenance.json`. Harness использует JPEG quality 90, сервер нормализации приложения — 88, contact sheet приложения — 85. Поэтому сравнение моделей выполнено внутри одного harness, а production-путь проверяется отдельно через настоящий API и интерфейс. Эти проверки не смешиваются в таблице. Ключи облачных моделей и платные вызовы не использовались.

При подготовке cache первая собранная из сетевых диапазонов копия 8B projector не прошла SHA256 и была отклонена. Модель запущена с заново скачанной целиком копией, которая прошла ожидаемый digest `85aa79666ee786bcc4fe69ac343db5ad468b71ad6272c12bfd8dfb29a8bdf18a`. Обе языковые модели и projector проверены по digest из manifest. Временные сетевые ошибки не включены в оценку модели и время инференса.

## Воспроизведение

Запуск модели с отдельным cache выполняет `scripts/start-model.ps1`. Он фиксирует digest модели и projector и проверяет SHA256 загрузок. Для уже скачанных файлов доступны `-RuntimeDir` и `-ModelDir`. Обычный запуск приложения описан в основном README.

```powershell
python evaluation/run_eval.py --model qwen3-vl:4b-instruct --variant plain --cases cap-single cap-multi suitcase-multi nike-conflict demix-annotations nike-select
python evaluation/run_eval.py --model qwen3-vl:4b-instruct --variant improved --no-catalog --label 4b-v3-reproduction --cases cap-single cap-multi suitcase-multi nike-conflict demix-annotations nike-select demix-gallery-select largest-gallery-select negative-blank negative-chart
python evaluation/run_eval.py --model qwen3-vl:4b-instruct --task ground
python evaluation/run_eval.py --model qwen3-vl:8b-instruct --variant improved --name-only --label 8b-name-only-reproduction --cases target-jacket nike-conflict negative-chart
python evaluation/refine_saved.py
python evaluation/summarize.py
```

Для 8B запускается соответствующая модель и меняется `--model`. Для сохранения опубликованного материала повторные серии лучше записывать с новым `--label`. Endpoint должен быть свободен от других запросов во время сравнения. Overlays показывают координаты именно на отдельных исходных кадрах. `summary.json` хранит компактное машинно-читаемое сравнение, а raw model responses доступны рядом с результатом каждого запроса.
